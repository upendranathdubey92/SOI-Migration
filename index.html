Why This Migration — The Gist

The one-paragraph version for anyone opening this doc: what we're changing, why it's worth doing, and what the business gets at the end.

Today most pages on spaceotechnologies.com — services, solutions, hire, landing — are hand-coded custom HTML (only blogs use Gutenberg). Every non-blog edit means a developer editing raw HTML. We go headless: WordPress becomes a content API, a new Next.js 14 front-end renders every page from reusable, field-driven components.

Why now

The problem today

  • Non-blog pages are hand-coded custom HTML — no Gutenberg.
  • Editing means changing raw HTML by hand — slow and easy to break.
  • Every page update needs a developer; editors are blocked.
Headless split

The payoff

After migrating

  • Editors update structured fields, not code — safe publishing on any page.
  • Faster site (Lighthouse ≥ 90) with 1:1 SEO across all 749 URLs.
  • Reuses the proven SOC v2 blueprint — lower risk.
Bottom line: non-blog pages go from developer-only raw HTML to field-based editing — faster site, same SEO, delivered in 18 weeks on a proven blueprint.

03 Architecture

Two repos, one contract: WPGraphQL. Content in WordPress, presentation in Next.js. Mirrors SOC v2.

Backend

soi-wp — headless CMS

  • WPGraphQL + ACF + JWT, Rank Math via GraphQL
  • FaustWP for previews & auth
  • 16 CPTs migrated with ACF field parity
  • Odoo lead endpoint stays PHP, called from Next.js
GraphQL

Frontend

soi-nextjs — presentation

  • Next.js 14 App Router (TypeScript)
  • Reusable components composed from ACF fields
  • ISR + revalidate webhook on WP saves
  • API routes: contact, calculator, sitemap, revalidate

05 Testing — Dev-Owned, 4 Layers

No dedicated QA. Devs write and run all tests; CI coverage gates enforce quality (≥ 70% on utils & critical components).

  • Unit (Jest + RTL). Utility functions, pure components, and the cost calculator (20+ input combinations vs legacy PHP). Runs on every commit.
  • Integration (Jest + MSW). Page components against mocked WPGraphQL, API routes, and the form → Odoo flow.
  • E2E & visual (Playwright). Top 100 URLs pixel-diffed; critical flows across Chromium, WebKit, Firefox on every PR.
  • Backend / contract (PHPUnit + WPGraphQL). Schema shape locked; SEO field presence checked per CPT.

Trade-off: with a 2-person team the peer-review pool is thin, so revenue-critical flows (calculator, Odoo lead form) get a cross-review from SOI's SEO / marketing owner before launch.

07 Top Risks & Mitigations

Worth flagging up front.

  • Single-owner build. Any absence in a critical week delays launch. Mitigation: detailed commit history and inline decisions so work can be picked up.
  • Templates are the critical path (~8 weeks sequential). One delay compounds downstream. Mitigation: freeze template scope after discovery — no mid-build redesigns.
  • SEO ranking dip at cutover. Mitigation: 749-URL redirect map, staging schema validation, Search Console resubmit within 24h.
  • Cost-calculator logic drift. Mitigation: snapshot tests vs 20+ legacy PHP outputs, plus double peer review before launch.
